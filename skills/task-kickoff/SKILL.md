# 킥오프

목표: 응시자가 **정확히 지시할 수 있게** 큰 그림을 먼저 주고, 그다음 "무엇이 되면 됐다고 보는가"를 확정한다.

## A. 첫 브리핑 (0:00–0:07) → 보고하고 멈춘다

읽기만 한다. 코드·파일 구조를 만들지 않는다. 데이터는 헤더, 행 수, 앞 3행, 고유값이 적은 열의 값 목록 정도만 빠르게 본다.
지시 문서 전부(루트 지시문, 데이터 설명서, 출력 스키마 문서, 그 밖의 `*.md`, 하네스 문서 제외)를 읽고 `BRIEF.md`를 쓴다.

```
# BRIEF
## 1. 한 줄 목표            무엇을 만드는 과제인지 한 문장
## 2. 만들어야 할 것          기능·화면·산출 파일 목록 (지시문 표현 그대로 짧게)
## 3. 하드 규칙              숫자 포함 그대로 (정원, 시각, 전원 배정 등) — 어기면 실패인 것
## 4. 운영자가 바꿀 수 있어야 하는 값
## 5. 금지·범위 밖·환경 제약   (업로드 금지, 특정 데이터만 사용, 범위 밖 기능 등)
## 6. 역할과 화면            역할별로 할 수 있는 일
## 7. 출력·제출물            출력 스키마 요약, 필수 문서와 양식 위치, 배포 요구 유무
## 8. 데이터 구조
   | 파일 | 한 행 = | 행 수 | 키 | 역할(마스터/기록/관계표/참고) | 과제에서 쓰임 |
   관계: A.x → B.x (1:N) …
   규모: 대상 수, 장소·자원 수, 기간
   ### 파일별 미리보기 (df.head 처럼)
   파일마다 열 이름 + 앞 3~5행을 마크다운 표로. 실제 값을 그대로 보여 준다.
   - 긴 값은 20자에서 자르고 `…`, 열이 10개를 넘으면 앞쪽 열 위주로 보여 주고 생략한 열 이름을 아래 한 줄로.
   - 표 아래 한 줄: 열마다 형식(정수/실수/날짜/시각/범주/ID)과 범주 열의 값 목록(적으면).
   - 앞 행만으로 패턴이 안 보이면(같은 사람 반복 등) 다른 대상의 행을 1~2개 섞는다.
## 9. 문제 유형 (잠정)        노선/배정/일정/선정·적재/문서 질의응답 중 무엇, 단계 분해
## 10. 눈에 띄는 함정 후보     문서와 데이터가 다를 것 같은 곳, "담당자 확인" 표시가 붙은 곳
## 11. 응시자가 정해야 할 것   해석·기준·우선순위 결정 목록 (선택지와 각 선택의 영향 한 줄)
```

- 숫자는 지시문·데이터에서 본 것만. 추측은 "(추정)" 표시.
- 응시자에게는 `BRIEF.md` 경로와 **핵심 5줄**(목표, 가장 중요한 하드 규칙, 데이터 핵심, 문제 유형, 가장 급한 결정 1~2개)만 보고하고 **지시를 기다린다**.

## B. 상세 킥오프 (응시자 지시 후, ~0:20)

1. **요구사항 매트릭스**: `docs/requirements.md`를 `AGENTS.md` 4절 형식으로. 요구 문장("~해야 한다 / ~할 수 있어야 한다 / ~하지 않는다 / 반드시 / ~까지 / ~이후")을 한 줄씩. 숫자는 설정값 후보. 보통 20~40줄, 10줄 미만이면 다시 읽는다.
2. **상세 데이터 점검**: `data-audit` 스킬. 결과로 `BRIEF.md` 8·10절을 보강(건수 포함).
3. **유형 판별 확정**: 계산·최적화는 `optimization-strategy`, 문서 질의응답은 `retrieval-qa`.
4. **함정 체크리스트**(아래)를 지시문·설명서 문장과 대조.
5. **담당자 질문 초안**: `stakeholder-questions`. 응시자가 보낸다.
6. **`PLAN.md`**: 단계표+실제 시각, 기술 스택, 시연 시나리오(응시자와 합의), **구역 지도와 경계면**(`AGENTS.md` 2-1), [가정] 목록. 구역 지도는 응시자에게 보여 주고 두껍게 만들 순서를 받는다.
7. `docs/decisions.md`(응시자 결정 반영), `docs/questions.md` 생성 → 첫 커밋.
참고 문서가 수십 페이지를 넘으면 `AGENTS.md` 4-1절 방식으로 색인부터.

## 함정 체크리스트

- [ ] "담당자에게 확인할 수 있다"가 붙은 항목 → 데이터에 그 차이가 숨어 있을 가능성이 높다.
- [ ] 문서에 열거된 범주값 vs 데이터의 실제 고유값.
- [ ] 날짜의 의미("기준일", "집계 기준"), 자정 넘김, 주말·휴일 행.
- [ ] "합산하지 않음", "반복됨" → 집계 시 중복 계산.
- [ ] "포함되지 않음", "관측되지 않음" → 이 데이터를 수요·정답으로 쓰면 안 되는 이유(잘린 값).
- [ ] 방향성·비대칭(A→B ≠ B→A).
- [ ] "반드시 이 값 사용" → 대체 계산 금지.
- [ ] "~하는 방식은 사용하지 않음" 같은 접근 금지.
- [ ] 같은 정보가 두 파일에 있을 때 어느 쪽이 우선인지(마스터 vs 날짜별 기록).
- [ ] 운영자가 바꿀 수 있어야 하는 값 → 하드코딩 금지 목록.
- [ ] 응시 환경 제약(업로드·파일창 금지, 전체화면, 미리보기) → UI 제약.
- [ ] 화면 요구에 숨은 계산(현재 위치, 남은 거리, 상태 표시 등).
- [ ] 제출 문서의 양식 위치와 필수 파일명.
- [ ] 배포 관련 요구가 있는지 없는지.
- [ ] "범위 밖" 목록.

## 시연 시나리오 합의

응시자에게 "제출 전에 직접 돌려 볼 순서"를 3~6단계로 받아 `PLAN.md`에 적는다. 이것이 완료 조건이다.
