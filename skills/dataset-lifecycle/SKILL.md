# 데이터셋 수명주기

## 흔한 요구와 구현

| 요구 | 구현 |
|---|---|
| 업로드 없이 선택 | 서버의 데이터셋 폴더(경로는 설정값) 아래 하위 폴더 하나 = 데이터셋. 원본도 목록의 한 항목 |
| 검증 | 선택한 폴더의 **실제 파일**을 읽어 스키마 검증. 결과를 파일·줄·열·사유로 |
| 실패 시 미적용 | 검증 실패 → DB 미변경, 현재 데이터와 결과 유지 |
| 모든 파일 변경 반영 | 적용 시 전 테이블을 **한 트랜잭션**에서 교체(자식 삭제 → 부모 삽입) |
| 현재 데이터셋 표시 | 상태 행: 현재 데이터셋, 버전 번호, 적용 시각 |
| 재계산 전 결과를 새 결과로 보이지 않기 | 결과에 데이터 **버전**을 저장. 현재 버전과 다르면 "재계산 필요" 표시, 이용자 화면은 경고 또는 조회 차단 |
| 결과·오류 하드코딩 금지 | 이름으로 분기 금지. 검증기는 스키마만 안다 |

## 검증기 설계 (작업 공간에서 작성)

- 스키마를 **데이터로** 정의: 파일 → 열 → {형식, 필수, 범위, 허용값, 참조 대상(여러 개 가능)}, 키, 쌍 완전성 등.
- 검사 순서: 파일 존재 → 읽기·인코딩 → 헤더(필수 열, 중복 열) → 행별 열 개수 → 값 형식·범위·허용값 → 키 중복 → 참조 무결성 → 쌍 완전성 → 업무 규칙(경고).
- **연쇄 오류 방지**: 참조 대상 ID 집합은 형식 오류가 있는 행의 ID도 포함해서 만든다. 셀 하나 오류가 수천 건 참조 오류로 번지지 않게.
- 같은 종류 오류는 앞 N건만 상세, 나머지는 건수 요약.
- 결과 구조: `{ok, errors[], warnings[], summary[{file,column,code,count}], stats{file:rows}}`, 이슈 = {file, line, column, code, message}.
- 오류(적용 차단)와 경고(적용 허용)를 나누는 정책은 담당자 답에 따른다.
- 제공 원본이 통과하지 못하면 스키마를 고친다(`data-audit` 마지막 절).

## 변형 데이터셋 준비 (재현 가능하게)

- 원본은 수정하지 않는다. 변형은 **레시피(JSON 등) + 작은 생성 스크립트**로 만들고 둘 다 제출물에 남긴다.
- 레시피 연산 예: 조건 행 수정, 표본 n개 수정(시드 고정), 행 삭제, 행 추가, 열 삭제·이름 변경, 셀 값 변경, 깨진 줄 추가, 파일 삭제.
- 각 변형 폴더에 설명 파일(이름, 설명, 기대: valid/invalid)을 두면 목록 화면에서 보여 주기 좋다. 단, 기대값으로 검증 결과를 정하지 않는다.
- 최소 세트: ① 상태·일정 등 **핵심 입력 변경(정상)** ② 모든 파일을 조금씩 바꾼 정상 데이터 ③ 필수 열 누락 ④ 없는 ID 참조 ⑤ 형식·범위 오류 여러 종 ⑥ 파일 누락.
- 생성 후 검증기로 돌려 기대와 맞는지 확인. 수정 0건인 연산은 조건이 틀린 것.

## API·화면 패턴

- 목록 / 검증(DB 변경 없음) / 적용(서버에서 **다시 검증** 후 트랜잭션) 세 동작.
- 경로 조작 방지: 데이터셋 ID는 목록에 있는 이름만 허용.
- 화면: 목록 → [검증] → 결과 표(종류별 건수 + 상세) → [적용](검증 통과 시에만 활성). 상단에 "현재: ○○ · 결과: 최신/재계산 필요".
- 대량 행은 일괄 삽입(행마다 객체 생성 반복은 느리다).

## 시연 절차 (실행 안내 문서에 그대로)

1. 원본으로 생성 → 결과 확인
2. 정상 변경 데이터셋 검증·적용 → "재계산 필요" → 재생성 → 변화 확인
3. 오류 데이터셋 검증 → 오류 목록 → 적용 거부 → 현재 데이터·결과 그대로
